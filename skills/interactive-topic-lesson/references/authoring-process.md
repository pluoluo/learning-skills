# 先审教学内容，再审呈现，最后审实际课件

用于新课和实质性教学改版。顺序为：知识深度与讲解计划 → 内容审核 → 呈现计划 → 呈现审核 → Web 实现 → 实现后的教学审核与浏览器检查。前一阶段的重大问题未解决，不能进入依赖它的阶段。环境、可达部署和工具检查可以提前做；不能先写一套课件页面再补教学理由。

这是作者的工作顺序，不是孩子必须经历的页面顺序。具体课程可以连续探索、先试后讲、比较改写或采用其他组织方式，不规定题数、页面数、时长和统一的交互模板。

## 1. 写清要理解什么，以及怎样讲清

先在私有作者目录写 teaching-plan.md，标明修订号。读取对应学科指导及 teaching.md、learning-design.md；此时不选择卡片、标签页、拖拽或动效。计划要让审阅者在没有网页的情况下判断教学是否成立，而不只是看到“理解概念、动手探索、深入思考”等标题。

按实际需要记录：

- **起点与边界**：用户原话、学习者已知与假设、本次要改变的理解、必要前置知识、明确暂不处理的范围。补缺与知识整理不必采用同一路径。
- **核心知识关系**：准确结论、成立条件、容易被省略的限制、与相邻概念的联系。深度体现在为什么这样判断、条件变化后会怎样、能用什么例子支持或反驳；不把成人术语、偏题难例或覆盖更多知识当作深度。
- **实际讲解内容**：写出关键解释的学生可见措辞、具体例子和推导/比较依据，说明该解释回应什么困难、何时提供。不能只写“展示原理”“给出提示”。先尝试还是先示范由目标决定；约定性规则如实说明，不为满足“为什么”编造因果。
- **思考任务与材料**：给出真实的题干、文本/数据/图形条件、学习者要作出的判断或产出、可能的合理答案与有吸引力的错误。说明从入门到核心问题究竟增加了什么思考，而不只是换数、换人名。
- **反馈与支架**：针对关键反应，写出具体解释与可行修改方向，区分初次作答、得到帮助和修改。开放表达要写明复核依据及实际提供的支持；只有一个待人工复核的文本框，并不能承担全部讲解与反馈。
- **新情境及证据**：给出适合本课目标的迁移任务或其他可辨认的变化，说明它能观察到什么、不能观察到什么。任务不必成为选择题，也不必全自动评分。

这些是教学决策，不是每项固定一段、每课固定几道题的表格。保留必要的完整材料与反馈，使别人能复查结论，避免用冗长泛论代替具体设计。

## 2. 第一轮只审内容，不替页面找理由

重新从目标、实际材料和可能反应出发审阅，记录在 teaching-plan.md 的审核部分：审阅方式、对应修订、具体问题、修改、复核依据和剩余限制。默认由作者另做一次自审；可用且已获授权的独立审阅可以补充，但不是安装或完成 Skill 的前提，不冒称独立审核。

审核重点：

- 核心关系和讲解是否正确，范围是否适合该学习者；每个关键解释是否有实际例子/依据，是否隐含未经确认的前置知识。
- 学生能否仅凭一个关键词、照着示范替换或反复试错完成所有任务；若能，原本要求的理解在哪里发生？找出最薄弱的任务并说明其不足。
- 选取核心任务，实际写出一个合适反应和一个有代表性的不充分反应，按计划走一遍解释、反馈和修改。不能以“这里会给针对性反馈”代替反馈内容。
- 新情境改变了什么关系或判断条件；如果只验证熟练度，应如实缩小目标，不能声称已覆盖迁移或深度理解。

发现知识错误、关键讲解缺失、目标与任务不对应、核心思考可被捷径跳过，或反馈无法支持修订时，退回修改。只在内容已达到本次目标且重大问题已解决后记录“可进入呈现设计”。此结论不等于真实学习效果验证。需要外部来源核实时遵循环境的资料检索要求，记录真正看过的材料；不得虚构教材依据。

### 任务真实性三问（必答）

在 teaching-plan.md 的“审核记录”逐项写下答案，不能只写“深入思考/动手探索”：

1. **这个任务允许答错吗**：逐个指出关键任务中满足已给条件却未达到目标的反应。如果结论由条件必然成立（如固定12块分给4人，不管怎样摆平均都是3），它只是演示，不能当作孩子独立理解的证据。
2. **最薄弱任务**是哪一个：靠背口诀或反复试错能否完成？写出实际捷径、保留/替换理由和证据限度，不能把点击和最终摆对当作思考发生。
3. **学后新能力与实际机会**：用一句话说孩子能做到以前做不到的什么，并指出活动中哪一次机会真的让孩子做它。起点未经观察时将“以前做不到”记作待检验假设。

采用能区分目标混淆的最小、最自然例子。不为制造难度硬凑极端数字；简单例子若不能区分混淆才增加必要条件。若任务涉及“这句话可能不对”，先写清是哪句话，不能仅用成人术语提高难度。

可照 [teaching-plan.example.md](teaching-plan.example.md) 写结构。三个真实失败模式的设计推演分别见 [固定总数构造](cases/fixed-total-mean.md)、[甲0题面歧义](cases/zero-wording.md)、[入口口诀题](cases/formula-entry.md)；它们不是学生效果验证。

例如英语第三人称单数：只列“he/she/it + s，拖词填空，再做六题”不足以通过内容审核。需要明确本课范围，说明在具体语境里怎样确定主语所指、怎样表达日常行为，以及学生如何在主语改变时保留意思并修改句子。可用 `Mia plays after school` 与 `Mia and Leo play after school` 检查“看见人名就加 s”的局限，并解释变化依据。是否加入否定句、特殊变化或更多句式由本课目标与基础决定，不把所有规则都塞进一课。这是一个内容设计例子，不是所有英语课的固定任务。

## 3. 再决定怎样让学生看见、操作与思考

基于已通过内容审核的修订写 presentation-plan.md。引用 teaching-plan 的修订号；用文字场景、简图或简短分镜即可，无需先做成 Web。把每个关键知识关系/任务映射到：

- 学生最初实际看见的材料与指令；哪些信息已给出，哪些仍需要自己找出或组织。
- 可以修改、构造、比较或表达的对象，以及操作前后的真实变化/不变量。
- 何时看到什么反馈、讲解和帮助；一条典型错误怎样得到支持并被修改。
- 需要保留的作品和理由、可核对的条件及需人工复核部分，依据 learning-evidence.md 选择实际支持的方式。
- 核心对象、操作和反馈在宿主实际高度预算内怎样呈现；较长材料怎样展开或滚动，而不删去教学所需内容。

选择交互必须说明它如何帮助观察本课关系。例如拖动应使一个有关的变化可观察；如果只是把四个备选答案从点击改成拖动，不能因此声称增加了思考。没有可自动评分的条件也不能把原任务偷偷降成选择题。

在同一文件记录呈现审核：用第一轮相同的实际任务和反应走查，确认呈现没有替学生完成判断、提前泄露要预测的答案、删除关键条件，或把复杂操作负担误当知识深度。查看错误反馈、帮助展开和新情境，不能只审首页构图。重大问题解决后记录“可进入 Web 实现”。若技术能力无法承载核心教学要求，回到计划修订并说明损失，不能以美观或实现方便通过审核。

### 冷读（实现前的硬性审查项）

冷读未完成、修改后未重读、仍有重大歧义或答案泄露时，不得开始课件专用HTML/CSS/JS。schema通过、浏览器可操作、数学正确都不能替代这一步。没有无设计上下文的读者时，允许保留计划草稿，冷读结论须为“待补”，不能自行改成通过。

### 屏幕文案独立块：冷读和实现核对的同一来源

在presentation-plan.md中只维护一个标记为 `student-facing-copy` 的JSON代码块；结构见 [presentation-plan.example.md](presentation-plan.example.md)。它是作者私有输入，不扩展lesson schema。数组中每项含唯一 `id`、可见状态 `state`、`text` 字符串映射。按屏幕/状态列出实际出现的**全部**文字，包括h1/小标题、题面、按钮、图中标签、输入默认值、状态行、提示、错误反馈和结束说明。动态文字须列出实际初始、关键错误/帮助状态样例，另说明变量来源；不要只给抽象占位符，让读者猜屏幕会显示什么。

“学生可见题面原文”字段指向这个块，不在另处手抄一份。冷读输入必须用下方工具抽取；实现时从该块逐项转入文案常量，实际浏览器校验也用同一抽取结果逐屏逐状态比对。特别清点实现新增的h1、重复标题、状态说明和计算中间量；实现多出的文字先补回块，检查泄露并定向重读，不能仅在review里说两者一致。工具不解析动态DOM，不会自动证明实现与块完全相同。

```bash
node scripts/screen-copy.mjs /path/to/author/presentation-plan.md --screens s1,s2 --out /path/to/private/cold-read.txt
node scripts/screen-copy.mjs /path/to/author/presentation-plan.md --screens s2,s3 --out /path/to/private/reread.txt
node scripts/screen-copy.mjs /path/to/author/presentation-plan.md --out /path/to/private/implementation-copy.txt
```

输出只含选中屏幕状态的文字，不带教学目标、审核意见或私有答案。第一轮先只给初始/待作答状态，让读者先复述行动，再按实际可见顺序给操作后/提示状态；不要一次把未来反馈的答案给读者。正确答案/提示只能出现在它实际显示的提交后/主动帮助状态，不能用这些后续状态替学生解释前面的预测屏。跨屏指代一起提供，保持可见顺序；实现校验可抽取全部状态。输出文件已存在时工具拒绝覆盖；修订后另存或直接用stdout抽取。

在 presentation-plan.md 的“审核记录”保留下面全部项目；缺任一项，人工审核可直接退回：

- **学生可见题面原文**：指向上述独立块及本次屏幕状态id；不能只转述设计意图。各记录字段均可同行或多行，空字段与仅注释不算记录。
- **冷读者与上下文**：交给没有设计上下文的读者（fresh-context subagent或人），仅提供这些屏幕文字和必要可见状态，不给教学目标、预期答案或要找的缺陷。记录读者身份类型和实际输入范围。没有这种读者时可先做作者冷读草稿，但须注明已知设计的限制，此项仍待补，不能伪装完成。
- **冷读复述**：保留读者原话“我要做什么、做完看到什么”，不要由作者替读者补成预期答案。偏差修正后再次只给修订屏幕文字冷读。
- **逐条理解偏差与修改**：逐条比对原话与预期，列旧句→可能误解→改句；没发现偏差也写实际比对依据。不得只填“已优化/清晰可读”。
- **术语与数字情境检查**：未解释的“反例、条件、证据、约束”等须替换或就地解释。核查“平均”是否被读成“实际每人”，数字是否只是为凑极端；优先自然、最小的区分例子。
- **答案泄露自检**（冷读前必填）：逐屏回答“可见文字是否包含待填答案或中间结果”。检查标题与目标是否冲突、开局是否已摆成目标答案、图中/状态栏是否印出待求量。例如第②屏要求自己求出10和5，题面或状态却先显示10、5，就须退回修改。记录每个量何时可见、是否仍留给孩子判断；示范/已请求的提示可以披露，但须明确它是有帮助的练习，不能计独立成功。此项是作者检查，不是关键词扫描或自动语义评分。
- **复读范围与结果**：有修改就做二轮；只重读修改过的屏幕状态及跨屏引用它们的屏幕，列id、改句和实际复述/新发现，不要求无关屏全量重跑。未修改时写“无修改”及依据；相关指代不清或目标关系改变时扩大范围。二轮仍有问题则保持退回，不能为了凑“两轮完成”放行。
- **冷读审核结论**：用“通过；…”、“退回；…”或“待补；…”明确记录当前修订的实际结果，不把另一修订的通过挪用过来。

这是开发过程中的**自审冷读**，即使使用fresh-context subagent，也不得写成独立教学审核、真实学生验证或学习效果通过。完整结构见 [presentation-plan.example.md](presentation-plan.example.md)。呈现审核结论须绑定本次修订；缺冷读输入/复述/偏差修改/术语数字检查，不能仅因schema或浏览器通过而放行。

两份私有计划在进入实现前运行 `node scripts/check-plans.mjs /path/to/author --require-approved`。检查结构和作者明确写下的结论，不判断答案、冷读真实性、题面语义或教学深度。三项结论“内容审核结论 / 冷读审核结论 / 呈现审核结论”均须以“通过”开头（后可分号说明）。仅检查记录完整性可省略该选项；完整但退回的计划也可以通过结构检查。

新课和实质性改版最终构建使用 `build.mjs lesson.json --out /path/to/build --require-plans /path/to/author`。它在写文件前拒绝缺项、退回/待补的计划，并生成私有plans-check.json，关联课件摘要、两份计划摘要和文案块摘要；不会自动把subject或learnerEffectiveness改为passed。旧课件仍可用不带此选项的原命令，不强制补计划，不改compile/validate或便携格式。

**顺序的实际边界**：构建门槛只说明构建时这些记录存在且作者声明通过，回执中 `chronologyVerified:false`。它不监控编辑器，不能证明画布尚未写过，也不能阻止作者绕过可选选项。若先有画布草稿后才完成P3，须在review的 `authoring order:` 中如实写明偏离和补审范围，不倒填时间、不宣称严格顺序已被机器证明。

## 4. 实现后重新检查教学是否真的发生

将审过的材料、任务与反馈实现到 lesson.source.json 和 canvas.html。源文件中的 objectives/learningDesign 是实现映射，不替代前两轮内容审核。

完成后分开检查：

1. **教学实现**：对照两个计划的具体修订，查看实际显示的解释、核心任务、关键错误反馈与新情境。实际走一遍合适反应和不充分反应，检查是否被按钮、标题、默认值、自动提示或评分逻辑绕过了应有的思考。静态正确的答案不代表互动承载了原设计。
2. **浏览器与界面**：使用现有浏览器工具检查可操作性、触控/键盘、宿主高度、展开、反馈、恢复和来回调整视口。按 browser-check.md 记录观察；截图和脚本通过不能代替第1项。
3. **边界与效果**：说明尚未观察到的能力；没有真实学习者试用，就不声称已经证明深入浅出或学习有效。家长试用后提供的具体反应应反馈到相应计划。

将实际教学检查依据写入私有 review.json 的 subject.evidence：计划修订、学科指导、检查的具体任务、发现和修复的问题及未验证范围。审过计划不会自动让最终 subject 变成 passed；只运行校验则保持 not_run。现有校验器只检查结构与报告形式，不机器判定教学深度或强制这些语义审核，不能把形式通过说成内容审核通过。

`subject.evidence` 继续使用现有字符串数组，不改schema。建议固定以下证据标签（写实际内容，未做则写未做，不能靠标签获得passed）：

```text
plan revisions: teaching T… / presentation P…；实际审过的任务与学科依据
student-facing prompt: 实际课件显示的完整题面原文（各关键状态分别列）
screen-copy source: 独立块摘要、抽取范围、实际渲染逐屏比对及新增/重复文字
cold-read paraphrase: 读者类型、仅看了什么、原话“我要做什么/做完看到什么”及修订号
fixed: 逐条误解、旧句→改句、术语与数字情境的检查及重读结果
answer leakage: 各待求量/中间结果何时可见，自检发现与修改
reread scope: 修改屏和跨屏引用的id，二轮实际发现和未解项
authoring order: 实际依赖顺序、是否先有画布及补审范围；无自动时间先后验证
implementation-plan differences: 实现与计划修订的差异；无差异也列逐项比对依据
limits: 最薄弱任务、支架/试错能做到什么、尚未观察到的能力
```

若实现后发现关键条件丢失，例如预测被自动填入、移位/补零提示泄露答案，必须回到 presentation-plan.md 修订并重审，随后再检查实现；牵动目标、讲解或评价时也回到 teaching-plan。不能只改代码后沿用旧计划的审核结论。在差异项记录发现、计划修订和实现复验，计划通过不能替代实现后审核。

修改知识结论、学习目标、材料、讲解或评价依据时，回到内容计划；只改变呈现但影响信息可见性、支架或证据时，重审呈现并检查是否牵动内容；纯样式/实现修复复用未受影响的计划并做相称检查。内容或课件更新后不能沿用旧修订的审核结论。重大问题经现有两轮修订仍未解决时，保留私有草稿并说明阻碍，不靠补写“已审核”交付。

默认由 Agent 连续推进这些工作，不要求家长逐轮审批。用户明确要求先看方案或某轮确认时，交付该阶段可读的具体结果并按要求等待；不把内部作者文件变成默认家长作业。
